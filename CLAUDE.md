# Правила работы для боевого бизнеса

Это `soynativo-sergio` — боевой проект, не песочница. Все правила ниже —
обязательны. При сомнениях — **спросить, а не додумать**.

## 1. Сначала контекст, потом код

Перед началом работы спрашивай контекст использования. Не «что починить», а
«куда это пойдёт»: отдельный сайт, embed в CMS, виджет — это меняет техническое
решение.

## 2. Молча игнорировать ошибки запрещено

Никогда не игнорируй ошибки фоновых процессов молча. Если `exit code != 0` —
объясни, почему это безопасно проигнорировать, или разберись.

## 3. Подсвечивай breaking changes

При переименовании файлов и изменении путей — явно говори пользователю, что
ломается. Пример: «раньше можно было вставить этот HTML целиком, теперь нужен
ещё CSS-файл рядом».

## 4. GitHub Pages — не продакшен

Не предлагай GitHub Pages как продакшен-хостинг для бизнеса. Это preview-
окружение. Для продакшена — Cloudflare Pages / Netlify / Vercel / собственный
сервер с CDN.

## 5. Перед мержем в `main` — Pull Request

Всегда PR с описанием: что менялось, почему, что может сломаться, как откатить.
Не сливать напрямую в `main` без PR, даже если правка маленькая.

## 6. Проверяй `.gitignore`

Перед коммитом проверяй, что в индекс не попало то, чего там быть не должно:
`node_modules/`, `dist/`, `.env`, `*.log`, build-артефакты без сознательного
решения коммитить.

## H. Деструктивные Git-операции — только с явного подтверждения менеджера

К деструктивным относятся: `git rebase`, `git reset --hard`, `git push --force`,
`git push --force-with-lease`, `git branch -D`, `git clean -fd`,
`git checkout -- <file>` поверх несохранённых изменений. Если возникает
дивергенция веток — собирай диагностику и жди решения, не разруливай сам.

## Текущее состояние проекта

- Ветка для интеграции: `claude/integrate-fix-css-module-0f8ED`
- Структура: `public/index.html` + скомпилированный `public/styles.css`,
  входной файл Tailwind — `src/input.css`
- Сборка: `npm run build` (Tailwind v4 CLI)
- **Не определено:** куда пойдёт лендинг (отдельный сайт / embed в
  `school.soynativo.eu` / CMS) — от этого зависят дальнейшие архитектурные
  решения. См. правило 1.

## Известные долги, которые я ввёл и не подсветил явно

- `public/styles.css` закоммичен как build-артефакт без CI-сборки. Решение
  «коммитить или гитигнорить + собирать в CI» с пользователем не согласовано.
- Раньше HTML был самодостаточным (Tailwind через CDN). Теперь файл требует
  `styles.css` рядом или предварительного `npm run build`. Если будешь
  отдавать HTML отдельно (в редактор CMS, письмо, превью) — это сломается.
